## 🛡️ Фаза 12: Аудит и Укрепление Серверной Безопасности (Server Security Audit & Hardening)

> **Базируется на документе:** `Аудит серверной безопасности.pdf`  
> **Принцип:** *Deny-by-default*, серверная валидация, защита от BOLA/IDOR, XSS, SSRF и утечек данных.

- [ ] **12.1 Аутентификация и Управление Сессиями**
  - [ ] Аудит API-эндпоинтов на вход без корректной сессии/токена.
  - [ ] Проверка валидации JWT-подписей, алгоритмов шифрования и параметров `exp`, `nbf`, `iss`, `aud`.
  - [ ] Исключение возможности использования Access Token в качестве Refresh Token и наоборот.
  - [ ] Гарантия полной инвалидации сессий при выходе (`logout`), смене пароля и сбросе доступа.
  - [ ] Исключение передачи токенов через URL, query string, referer, открытые логи и ошибки.

- [ ] **12.2 Серверная Авторизация и Защита от IDOR/BOLA**
  - [ ] Реализация обязательной серверной проверки прав для каждого эндпоинта (`/api/bookings`, `/api/parent/*`, `/api/admin/*`).
  - [ ] Строгая проверка принадлежности объекта (`booking_id`, `slot_id`, `user_id`) авторизованному пользователю из проверенной серверной сессии.
  - [ ] Запрет выполнения административных функций напрямую через API пользователями без роли админа.
  - [ ] Защита от уязвимости Mass Assignment: серверное формирование чувствительных полей (`status`, `role`, `price`).

- [ ] **12.3 Защита от Повышения Привилегий (Privilege Escalation)**
  - [ ] Исключение возможности изменения собственной роли на `admin` или присвоения чужих объектов.
  - [ ] Игнорирование клиентских флагов и полей `role`, `is_admin`, `status`, `owner_id` при обычном вводе данных.

- [ ] **12.4 Безопасность Внешних Запросов и Вебхуков (SSRF)**
  - [ ] Анализ всех точек отправки внешних HTTP-запросов (Telegram API, загрузка ресурсов).
  - [ ] Настройка allowlist разрешённых доменов и схем (`https://api.telegram.org` и т.д.).
  - [ ] Запрет опасных схем (`file://`, `gopher://`, `ftp://`) и обращения к служебным IP (`localhost`, `127.0.0.1`, private/link-local IP, metadata endpoints).
  - [ ] Ограничения по таймаутам, максимальному размеру ответа и числу редиректов.

- [ ] **12.5 Предотвращение Утечек Данных (Data Leakage & Error Handling)**
  - [ ] Аудит ответов API, ответов ошибок и серверных логов на отсутствие утечек персональных данных, API-ключей, паролей, stack trace и внутренних путей БД/ФС.
  - [ ] Использование явных Response DTO/схем вместо прямого возврата сырых объектов базы данных.
  - [ ] Безопасные обезличенные сообщения об ошибках для клиентов с логированием детальных стеков только в закрытые серверные логи.

- [ ] **12.6 Защита Служебных Эндпоинтов и API-Маршрутов**
  - [ ] Закрытие или отключение в production служебных маршрутов (`/metrics`, `/status`, `/debug`, `/actuator`, `/swagger`, `/graphql`).
  - [ ] Отсутствие раскрытия переменных окружения, топологии сети и внутренних токенов через отладочные ручки.

- [ ] **12.7 Защита от XSS и Blind XSS в Административных Интерфейсах**
  - [ ] Экранирование и контекстная фильтрация всех пользовательских данных (имена родителей, детей, комментарии), отображаемых в панелях `/admin`, сообщениях Telegram и уведомлениях.
  - [ ] Полный запрет или строгая очистка (sanitization) `innerHTML` / `dangerouslySetInnerHTML` и Markdown-разметки проверенной библиотекой.
  - [ ] Защита администраторских сессий от перехвата и CSRF.

- [ ] **12.8 Защита от Open Redirect**
  - [ ] Валидация параметров перенаправления (`redirect`, `next`, `return_url`): использование только относительных внутренних путей приложений (`/my-dashboard`, `/admin`).
  - [ ] Запрет редиректов на внешние домены, защищённые от оборачивания URL, двойного кодирования и поддоменов злоумышленников.

  - [ ] Внедрение серверного лимитирования частоты запросов (Rate Limiting по IP и авторизованному пользователю) для ключевых эндпоинтов:

  - [ ] Использование только параметризованных запросов Supabase ORM / Client.
